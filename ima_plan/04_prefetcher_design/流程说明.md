### **前提：**

### 具体说明
#### **训练阶段：**
 warp 0 发出一个 regular LDG，被 dependency detect 部件记录，首先判断出它的源寄存器并不是某个前序 IMAD.WIDE 的目的寄存器，所以记录它的目的寄存器。**然后发现它的目的寄存器被非 IMAD 指令作为源寄存器了**，说明这条 load 指令不是 IMA，所以不再追踪其依赖链。如果此时其他 warp也发射了这条 regular load，因为已经存在表中，所以不会进表（这是降低硬件开销的要求，如果每个 warp 都追踪，不仅耗费额外的硬件资源，训练的 PC 还是一样，没有必要计入；或者每个依赖链都记录两组 warp，以此来增加置信度，而代价是额外多一个 warp id，即这个表项对两个 warp的同一依赖链都会记录，但是对于去掉的逻辑，只要任意一个 warp 发现不满足，则直接去掉）；
> 这里带来一个额外的选项，是否记录那些非 IMA LOAD 指令，以减少 dependentncy detector 的功耗，代价是一个每次进表前一个大的比较，可能会造成延时的压力。  

warp 0 发出 load 后，因为第一次肯定 miss，所以会有较大的延时，这时其他 7 个 warp 也发出来这个 regular load，根据上面的策略决定 dep detector 的行为，但是核心肯定是减少这些 warp 的 load 的进表  
然后真正的 warp 0  IMA idx load 发起，正常进表，PC 也需要进表（**只需要挑选一个 lane 就足够了，因为所有 lane 共享一个 stride**），用来推断 stride。等待值的返回，其他 7 个 warp 也发出这个 idx load。**对于 LDG.E 指令，先判断它的源寄存器是否来自 IMAD.WIDE 指令的目的寄存器，是的话按照下面流程走；不是的话进表检测等待后续指令流检测是不是 idx load**
warp 0 ix load 按理来说会先返回，然后这个 warp 继续发射，发射到对应的 IAMD.WIDE pc，dep detector 检测到这条指令的源寄存器属于前面的 LDG 的目的寄存器，把这个 IMA.WIDE 指令进表，记录它的源操作数和目的寄存器。对于正常的 IMAD.WIDE 指令，如果源操作数没有常量缓存，或者源操作数没有来自表中记录的 LDG.E 指令的，直接不进表  
IMAD.WIDE 指令很快就完成了，这时 warp0 会发射 LDG.E_data，此时 dep detector 会检测到这条 load 指令的源操作数是来自上一条 IAMD.WIDE 的目的寄存器的，所以进表，依赖链训练完成，但是此时这个依赖链的信息还不进入 CT/TT，因为 strde 并没有 valid
**此时 warp 1-7 的指令应该不会进表，或者额外有一个 warp 进表增加 confidence**  

然后 warp 0 执行第 2 次循环，此时第一个表项的 idx LDG.E 再一次被 issue，通过相减就可以得到 idx load 的 stride，此时整个依赖链的就训练好了，要把 dep detector fifo 中的信息送入 CT/TT，其中 CT 中存三个依赖指令的 pc 和依赖关系，stride 大小，TT 从 IMAD.WIDE 指令中记录 ima data 数组的 baseaddr 和 element width。对于其他的 IMA 依赖链也是类似的操作  

#### 预取过程
第 2 次循环得到 idx stride 后就可以直接进行预取了，在获得了 stride 后，就可以计算出第三次 idx load 的地址，可以进行预取，通过 addrgen 模块计算出地址后，进行预取。**注意，这里预取的单位是 warp，发起请求的 lane 则采用第二次循环中所有活跃的 lane**，addrgen 内有 coalscer 组件，把请求聚合成 sector 发出，同时还包含 pending buffer 的 entry id （@ima_plan/05_implementation/v1_implementation_problems.md），组件里还会有一个 pending buffer，用于记录 inflight 的 idx load， 每次 idx 预取请求会在这个 buffer 中分配一个表，记录有多少 lane 个结果需要返回，以及这个依赖链对应的 TT id。同时从这里发出的 idx load 请求会带有标记，返回给 prefetcher 单元而不是 LSU。当第一组 lane 结果返回时（cache 直接返回结果，且有对应的 pending buffer entry ID，而且有可能一个 cycle 返回多个 idx），直接根据 Table b id 索引表项，由得到的 baseaddr 和 element width 计算出对应的 ima data 的地址，并发起预取。直到所有 lane 都返回，这个 entry 就可以 pop 掉了。

#### 可能需要考虑的问题
1. 对于一些只执行一次的 ima，如果不清理，会造成僵尸 entry，所以我认为需要加入一些定期清理机制，如果多个后进表的 entry 都训练好了，前序还有没训练好的，就要及时清除；或者你有什么更好的解决办法
2. 当发生 kernel 切换时，需要清除预取器的训练表项，因为不同 kernel 的 PC 不同
3. 当 CT/TT 都满了，还有新的依赖链要进来，如果此时表中没有活跃的表项，可以用 LRU 替换，但是在实验中我们可以把表项设置大于所有测例的 IMA 依赖链来避免这个问题（不能在论文里这么说）
