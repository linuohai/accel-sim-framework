# Introduction 写作 Golden Rules

> 最近更新: 2026-04-04
>
> 来源: 知识星球视频总结包（8 讲）— 提炼的核心写作原则
>
> 用途: 指导 GRASP 论文 Introduction 的撰写与自检

本文档按 Introduction 的写作流程组织，从动笔前的标题拆解到最后的收口闭环。每条原则包含四个层次：

1. **是什么** — 原则的精确定义
2. **怎么做** — 操作方法 + 8 讲中的原始例子
3. **为什么** — 背后的认知/逻辑原理
4. **GRASP 映射** — 标注 ✓/✗/⚠️ 的本论文具体应用

---

## §0 前置：标题拆解与两条贯穿全文的原则

> 在动笔前执行，为整个 Introduction 奠定逻辑基础。

### 标题拆解方法

**是什么**：把标题拆成四类成分——研究对象、贡献性词、方法词、修饰词。这是后续所有判断的前提。

**怎么做**：

- 先识别「研究对象」（标题中指向你要解决什么问题的核心名词短语）
- 再分离「贡献性词」（体现作者独有创新的词）、「方法词」（具体技术路径）、「修饰词」（限定范围的形容词）
- 围绕研究对象列出**上位概念链**：从最广泛的领域逐层收窄到你的具体对象
- 原始例子（第 1 讲）：范文标题被拆成"实现手段、方向词、作者贡献、研究对象"四类，再列出上位概念链判断前言应从哪一层切入

**为什么**：标题是全文逻辑的浓缩版。不拆标题就动笔，写出来的前言容易跑偏——因为你不知道自己的逻辑终点在哪里。上位概念链决定了前言的逻辑速度（从哪层开始、经过几层到达研究对象）。

**GRASP 映射**：

```
标题: GRASP: Grasping GPU Indirect Memory Patterns
       via ISA-Exposed Register-Chain Prefetching

拆解:
  研究对象  = GPU Indirect Memory Patterns
  贡献性词  = Grasping（主动捕获）、ISA-Exposed（核心 insight）
  方法词    = Register-Chain Prefetching
  修饰词    = GPU

上位概念链:
  Irregular computation / Memory bottleneck
    → Prefetching
      → GPU Prefetching
        → IMA Prefetching
          → ISA-exposed IMA detection
            → GRASP
```

### 原则一：句句指向标题

**是什么**：前言里的每一句话都要和标题直接相关，或者为引出标题中的某个概念**显式承担铺垫功能**。不能出现与标题完全脱节的孤立句子。

**怎么做**：

- 写完每句话后自检：这句话里提到了标题中的哪个词？如果没有直接提到，它是在为标题中的哪个概念做铺垫？
- 如果两个问题都答不上来，这句话应该删掉
- 原始例子（第 1 讲）：检查前言开头每一句话——"它要么直接对应标题，要么必须明确承担铺垫功能"

**为什么**：前言不是宣传页，是对全文研究边界的提前立约。每一句游离的话都在消耗读者注意力，同时给审稿人留下"文不对题"的攻击点。

**GRASP 映射**：

- 每句话必须能追溯到标题中的某个关键词：GPU / Indirect Memory / ISA-Exposed / Register-Chain / Prefetching
- ✓ 讨论 "GPU warp 交织使 pattern detection 困难" → 指向 GPU + 为 Register-Chain Prefetching 的必要性铺垫
- ✓ 讨论 "图计算的不可替代性" → 指向 Indirect Memory Patterns 的普遍性
- ✗ 详细讲 GPU 在 AI training 中的加速效果 → 与 IMA prefetching 无关，删掉

---

### 原则五：字字有关联（全文贯穿）

**是什么**：你写下的每个词——包括性能描述、优势声明、应用场景——后文都必须有对应的实验结果、数据或机制来呼应。如果你提到一个优点但后文没有结果支撑，就是主动给审稿人递刀子。

**怎么做**：

- 这条原则**从第一句的第一个关键词就开始生效**，不是到文献点评才管
- 检查前言中的每个性能词（"高效""低开销""通用"）、每个场景词（"图分析""稀疏计算"）：后文是否有结果呼应？
- 如果没有对应结果，**删掉这个词**，而不是留着碰运气
- 原始例子（第 1 讲）：范文写了"高倍率性能""宽温域"，因为它有对应实验；如果你的工作没有这些内容，照抄就是逻辑失真
- 进阶例子（第 7 讲）：两篇论文都研究"可充电电池"，但一篇面向大规模储能/电动车，另一篇面向柔性/可穿戴设备。不能借用前者的背景句来写后者——因为连应用例子的措辞颗粒度都不匹配

**为什么**：审稿人会逐词对照你的 claims 和 results。前言中承诺了但 evaluation 没兑现的东西，是最常见的退稿理由之一。这条原则的本质是：**前言是契约，不是广告**。

**GRASP 映射**：

- ✓ "IMA 占 L1 miss 51-84%" → Evaluation 有 5 workload 的 IMA miss 分解数据
- ✓ "首个现代 GPU 通用 IMA prefetcher" → 在 SM80/A100 上评估 + 跑了多种图算法
- ✓ "Ideal L1D 天花板 1.75×-3.04×" → Evaluation 有 ideal L1D 对照实验
- ⚠️ "图分析、稀疏线性代数、推荐系统" → 只评估了图算法，没评估推荐系统 → 要么删掉推荐系统，要么改为更泛化的表述
- ⚠️ 不能在前言中声称 GRASP "解决了" SpMV 的 x16 展开问题，因为实验显示 SpMV stride 学习仍有设计瓶颈

## §1 第一段：问题定义与首句切入

> 这一段的任务：告诉读者「你的研究对象是什么，为什么重要」。

### 原则二：金字塔从上位到下位

**是什么**：概念推进必须遵循**从广到窄的层级结构**。一旦从上位概念下降到下位概念，不能又退回更高的层级。逻辑方向是单向收束。

**怎么做**：

- 先列出概念层级（在 §0 标题拆解中已完成），然后按层级顺序写
- 每写一句话，标注它在概念链上的位置，确认没有回跳
- 原始例子（第 1 讲）：先从"可充电电池"（第一上位）写起，逐步收窄到"水系电池"再到"锌锰电池"（第零上位），不会写完锌锰电池再跳回去讲通用电池

**为什么**：读者的认知是跟着你的逻辑路径走的。如果你东跳西跳，读者要不断重建上下文，阅读体验极差。金字塔结构让读者在任何一句话处都清楚"我现在在哪一层"。

**GRASP 映射**：

```
层级 1: "图分析/稀疏计算中广泛存在 IMA 模式"         (Irregular computation)
  → 层级 2: "IMA 打破所有传统 locality 假设"           (IMA problem definition)
    → 层级 3: "IMA 在 GPU 上尤其严重：三重打击"         (IMA on GPU)
      → 层级 4: "IMA 占 L1 miss 51-84%, ideal 1.75-3.04x" (定量证据)
```

- ⚠️ 不能在写完 GPU 的 IMA 问题后，又退回去泛泛讨论"不规则计算的分类体系"

---

### 原则三：进入正题的速度要适中

**是什么**：好的前言通常只经过 **2-3 层**上位概念就进入研究对象。不是所有层级都必须一层不落地写出来。

**怎么做**：

- 判断依据：**读者对这一层是否已经足够熟悉？**
  - 如果是（如 MICRO 读者都知道 GPU 有 cache hierarchy），一句话带过即可
  - 如果不熟悉但又必须理解（如 IMA 的定义），多写两句展开
- 越宏观越熟悉的概念越不需要占篇幅；越具体越陌生的概念越值得多写
- 原始例子（第 2 讲）："不是所有上位概念都要写，关键是判断读者是否已经足够熟悉"。越宏观的概念，一句话立住即可；相对小众的概念才值得用两句甚至更多展开

**为什么**：篇幅是稀缺资源。在读者已经知道的事情上花太多笔墨，会让人觉得你"说了半天没到正题"。进入正题的速度本身就在传递你对读者的判断力。

**GRASP 映射**：

- MICRO 读者对 GPU memory hierarchy 非常熟悉 → 一句话足够（"GPUs rely on massive warp-level parallelism to hide memory latency"）
- MICRO 读者对 IMA 的定义未必清楚 → 需要明确定义 `A[B[i]]` 模式并解释为什么传统 prefetcher 失效
- 不需要从"摩尔定律"或"GPU 发展史"起笔——这些离标题太远

---

### 原则四：起点不要离标题太远

**是什么**：前言第一句话的概念层级，与标题中最高层概念之间的距离必须合理。像"能源危机""全球变暖"这种万能开头，如果和标题中最高层概念还隔着很多层，就不该用。

**怎么做**：

- 数一下第一句话的概念层级到标题最高层概念之间有几层
- 如果超过 2 层，考虑砍掉开头
- 原始例子（第 1 讲）："删除所有离标题太远的'万能开头'"

**为什么**：开头太远不仅浪费篇幅，还会给读者一种"这篇文章要讲什么"的困惑。审稿人只看第一段就会形成"这个人知不知道自己在写什么"的初始印象。

**GRASP 映射**：

- ✓ 好的起点："Graph analytics, sparse linear algebra, and recommendation systems increasingly rely on GPUs..." — 直接从 GPU + Irregular computation 切入，与标题仅隔 1 层
- ✗ 不好："The explosive growth of data in the modern era has created unprecedented computational demands..." — 太泛了，和 IMA prefetching 隔了 4-5 层
- ✗ 也不好："Since the invention of GPU computing in 2007..." — GPU 发展史和 IMA prefetching 关系太间接

## §2 铺垫过渡：从读者熟悉到作者对象

> 这一段的任务：从读者的已有认知出发，自然地过渡到你的研究对象所在的领域。

### 原则六：铺垫必须值回票价

**是什么**：如果一句话不是直接讲标题里的东西，那它必须承担**明确的铺垫价值**，而且这个价值要大于它拖慢进入正题的副作用。铺垫不是"多写一点显得丰富"。

**怎么做**：

- 对每句非标题直接相关的话做**成本收益分析**：不写它会怎样？写它带来的理解收益是否足以抵消拖慢节奏的代价？
- 如果答案是"不写也行"，删掉
- 原始例子（第 2 讲）：范文标题讲锌锰电池，却先讲锂离子电池。看似跑题，但锂电池是读者最熟悉的对象，借它做认知桥梁的收益大于拖延代价 → 值回票价

**为什么**：审稿人的耐心是有限的。每句不直接相关的话都在消耗这个耐心预算。只有当铺垫的理解收益明显超过消耗时，才值得写。

**GRASP 映射**：

- ✓ 值回票价：先简要提及 stride/stream prefetcher 在规则负载上的成功（读者熟悉），再指出 IMA 为什么打破这些假设 → 帮读者理解 gap 的深度
- ✗ 不值票价：详细描述 GPU cache hierarchy 的发展历史 → MICRO 读者都知道，纯浪费篇幅
- ✓ 值回票价：花一句话提到 Gunrock/cuGraph 等 GPU 图框架的广泛采用 → 建立"GPU 上跑图算法是主流趋势"的认知

---

### 原则七：借读者熟悉的对象做认知桥梁

**是什么**：写作不是按作者脑内知识展开，而是**按读者能否顺畅跟上的路径展开**。先用读者最熟悉的对象建立认知抓手，再把讨论推向你的研究对象。

**怎么做**：

- 先判断：读者看到你的研究领域时，脑海里最先冒出的概念是什么？
- 从那个概念出发，通过逻辑过渡引向你的研究对象
- 原始例子（第 2 讲）：读者看到"电池"会先想到锂离子电池 → 范文先借锂电池做抓手 → 再引出"那有没有别的储能体系" → 最后落到水系锌锰电池

**为什么**：人的认知是锚定式的——总是从已知出发理解未知。如果你直接抛出一个读者不熟悉的对象，他们需要自己去建立和已知概念的关联，这个过程很容易失败。你帮他们做这一步，理解效率翻倍。

**GRASP 映射**：

- 读者（MICRO 社区）最熟悉的 prefetching 对象：stride prefetcher / stream prefetcher / next-line prefetcher
- 认知桥梁路径 1：先说 "GPU prefetching 已有 15 年研究（Many-Thread→CAPS→Snake），在 stride pattern 上取得了成功" → 再说 "但面对 IMA 的数据依赖，这些方案全部失效" → 自然引出 "需要专门的 IMA prefetcher"
- 认知桥梁路径 2：先说 "CPU 社区对 IMA 有 10 年积累（IMP→DMP→Tyche）" → 再说 "但 CPU 假设无法迁移到 GPU" → 建立 "GPU IMA prefetching 是空白" 的认知

---

### 原则八：批评要客观、克制、有证据

**是什么**：涉及比较、指出已有工作的不足时，必须确保表述**客观、事实充分、措辞克制**。不能带攻击性。

**怎么做**：

- 用 "challenges remain" 而不是 "fundamentally flawed"
- 用 "has not been explored" 而不是 "has been completely ignored"
- 必须紧跟具体证据（数据或事实），不能空口下判断
- 原始例子（第 2 讲）："不要轻易写'替代锂电池'这种攻击性很强的话。你一旦这么写，就等于把大量锂电研究者一起得罪了。"
- 原始例子（第 3 讲）：指出问题时用 "challenges" 这类克制表达——"你越克制，反而越不容易被抓话柄"

**为什么**：(1) 审稿人可能就是被你批评方向的研究者；(2) 过度夸大 gap 会让审稿人质疑你的学术判断力；(3) 克制反而增加可信度——用证据说话比用形容词说话有力得多。

**GRASP 映射**：

- ✓ 克制："these approaches assume single-threaded address streams, which does not hold on GPUs" — 事实陈述
- ✗ 不克制："CPU approaches are completely useless for GPUs" — 攻击性
- ✓ 克制："[Spare Register] was designed for Fermi (2010) and supports only single-level load-pairs" — 客观限制
- ✗ 不克制："Spare Register is obsolete and poorly designed" — 伤害性
- ✓ 最佳实践：用人家自己论文的声明来支撑你的判断 — "CAPS explicitly excludes data-dependent accesses [Koo, IPDPS'18]"

---

### 原则九：半定量审查

**是什么**：凡是用了"很多 / 主流 / 关键 / 普遍 / 核心"这类量化暗示词的地方，都必须做**比例验证**。如果实际只占 20-30%，不能说"主流"。

**怎么做**：

- 写完后扫描所有量化暗示词
- 对每个词追问：实际占比是多少？是否真的达到了这个词暗示的比例？
- 原始例子（第 2 讲）：你说"主流""普遍"，最好真的接近大多数（>70-80%）。只占两三成时应该用 "some" 或 "certain"

**为什么**：审稿人特别喜欢攻击这类词。你说"大量工作采用了..."，审稿人只需要举一个反例就能动摇你的可信度。半定量审查可以预防这类低级失分。

**GRASP 映射**：

- ✓ 有数据支撑："IMAD.WIDE chains cover 88.4% of IMA dependency chains across 56 implementations" — 有精确数据
- ✓ 有实测范围："IMA accounts for 51%–84% of L1 misses" — 5 workload 实测
- ⚠️ 需审查："widely used in graph analytics" — "widely" 需要引用 Gunrock/cuGraph 的采用数据
- ⚠️ 需审查："most GPU prefetchers target stride patterns" — 列出的 4 代确实都是 stride-based，可以更精确地说 "all four generations of GPU prefetchers"

## §3 第零上位引出与第一性原理

> 这一段的任务：把研究对象落地，建立「这个对象值得研究」的共识，并指出当前的 gap。

### 第零上位概念

**是什么**：标题中的核心研究对象（"第零上位"）必须在前言某个**关键节点**被明确引出。这个节点标志着前言从上位铺垫正式收拢到你的研究对象。

**怎么做**：

- 当前文已经完成更高层概念的铺垫后，用一句话明确落到研究对象
- 这句话通常同时承担**多个功能**：引出对象、交代研究价值、指出待解决问题、埋下标题呼应点
- 原始例子（第 4 讲）：第三段第一句把第零上位"锌锰电池"引出来，同时说明它为什么值得研究、卡在哪里。"同一句话里同时承担'引出第零上位、交代研究价值、指出待解决问题、埋下标题呼应点'四个任务"

**为什么**：如果标题写了研究对象但前言迟迟不处理它，读者会觉得标题和正文没对上。第零上位的出场是前言逻辑链的一个关键锚点。

**GRASP 映射**：

- 第零上位 = "GPU IMA hardware prefetcher"
- 落地节点：在描述完 CPU IMA 方案无法迁移 + GPU prefetcher 从未触及 IMA 之后，钳形闭合的那一刻
- 落地句："GPU IMA prefetching remains an open problem"
- 这句话同时承担：
  - 对象落地（GPU IMA prefetcher）
  - 研究价值（大量性能损失待回收）
  - 问题指出（是交叉空白）
  - 标题呼应（指向 GRASP）

---

### 隐含修饰识别

**是什么**：标题字面的研究对象可能比你实际研究的更宽泛。作者故意不在标题中写出所有限制条件（为了保持论文的适用范围），但在正文中必须**逐步引出这些隐含限制**。

**怎么做**：

- 结合正文实际研究内容，判断真正的研究对象是否比标题更具体
- 如果是，在分析时写成带括号的补全形式，如"（柔性固态）可充电锌空气电池"
- 在前言中用逻辑过渡自然引出这些隐含限制
- 原始例子（第 7 讲）：标题说"可充电锌空气电池"，实际研究"柔性固态可充电锌空气电池"。标题不写全是因为方法具有普适性，写全了反而把文章格局写小

**为什么**：直接在标题中写出所有限定词会不必要地缩窄论文适用范围。但如果在正文中不提前铺垫，读者在后文看到这些限定词时会感到突兀。

**GRASP 映射**：

- 标题说 "GPU Indirect Memory Patterns" — 泛指所有 GPU 上的 IMA
- 实际聚焦 = **(Graph workload 的 IMAD.WIDE-based)** GPU Indirect Memory Patterns
- 隐含限制 1：主要在 graph workloads 上评估（BFS/SSSP/BC/CC/SpMV），而非所有 IMA 场景
- 隐含限制 2：检测依赖 IMAD.WIDE 指令，不覆盖非 IMAD.WIDE 的 IMA（如 SCC 的系统性反例）
- 处理方式：在前言中先建立"graph workloads 是 IMA 最典型的应用场景"，再提到 IMAD.WIDE 覆盖率 88.4% — 让读者理解为什么聚焦于此

---

### 删除测试

**是什么**：判断一个词/概念要不要在前言中提前铺垫的**最实用标准**：把它从前文中删掉，假设它在后文第一次出现时才露面。读者会不会觉得突兀？会 → 需要铺垫；不会 → 可以省略。

**怎么做**：

- 对标题中的每个关键词和后文会重点展开的术语，做一次删除测试
- 原始例子（第 7 讲）：如果"Gel Electrolyte"不在前言中提及，后文突然出现会让读者困惑 → 需要铺垫。"把这个词从前文铺垫里删掉，假设它在后文第一次出现时才露面。如果读者会立刻产生'这个东西怎么突然冒出来了'的感觉，那它就应该在前言中被提前埋下"

**为什么**：比死背模板更灵活。这条标准适用于各种长标题、多修饰语的情况。铺垫不是看词有多高级，而是看它在后文首次出现时，是否会打断读者理解路径。

**GRASP 映射**：

- ✓ 需要铺垫："IMAD.WIDE" — 如果前言完全不提，§4 Design 突然出现这条指令名读者会困惑
- ✓ 需要铺垫："Register-Chain" — 如果不铺垫 index→data 的寄存器依赖关系，后文检测机制让人摸不着头脑
- ✗ 不需要专门铺垫："Stride prefetcher" — MICRO 读者都知道
- ✗ 前言点到即可："(base, scale) 归并" — 具体设计细节，不需要提前定义

### 原则十：真实世界的第一性原理

**是什么**：面对技术判断（尤其是优缺点评价），**不能因为文献这么写就跟着写**。更稳的做法是先回到真实世界验证：这个说法是否符合基本常识、真实应用和客观约束。

**怎么做**：

- 验证顺序：**(1) 先找真实系统/规格书/商业产品验证** → **(2) 如果无法直接判断，找高可信度文献**（综述、教材、高引论文）
- 不能只因为"某篇论文这么说"就当作事实
- 如果文献之间在相近条件下给出矛盾结论 → 这往往是一个值得做的新问题
- 原始例子（第 3 讲）：说"铅酸电池低电压" → 先看真实铅酸电池的电压规格验证，而不是只引用一篇论文的说法。"面对一个技术判断，不能因为文献这么写就机械地跟着写"

**为什么**：文献可以当支撑，但不能当脑子。学术写作的核心能力是**判断力**，不是引用量。你会不会做判断，决定了你能不能驾驭 AI 生成的文本和别人给你的素材。

**GRASP 映射**：

- ✓ "A100 每 SM 最多 64 warp" → 可直接从 NVIDIA spec 验证
- ✓ "IMAD.WIDE 是唯一能单指令完成 32×32+64→64 宽乘加的指令" → 可从 SASS ISA 文档验证
- ✓ "L1 miss rate 70-77%" → 来自实际仿真数据
- ⚠️ 说"CPU IMA prefetcher 无法迁移 GPU"时，不能只说"文献没做过"。要给出结构性原因：warp 交织破坏地址流清晰性、per-warp 复制存储不现实等 — 这些都可以用 GPU 微架构参数做第一性原理推导

### 原则十一：避免前后打脸

**是什么**：前面夸了一个对象的优点，后面再指出问题时，**优缺点必须落在不同维度**。不能前面刚说 X 好，后面就说 X 不好（同一维度）。

**怎么做**：

- 写问题陈述前，回看前文对同一对象的正面描述
- 确认正面和负面描述落在不同维度
- 原始例子（第 3 讲）：可以说"锌空气电池安全、低成本"（维度 A）但"循环寿命受限"（维度 B）→ 不矛盾。不能说"高能量密度"后又说"低能量密度"。"前面如果说某体系安全、低成本，后面再指出它的问题，就必须明确问题落在哪个维度"

**为什么**：前后矛盾是审稿人最容易抓的逻辑漏洞，而且一旦被抓住会严重损害全文可信度。

**GRASP 映射**：

- ✓ 不矛盾：说 GPU stride prefetcher "在规则负载上有效"（维度：stride pattern）→ 再说它"无法处理 IMA"（维度：IMA pattern）→ 不同 pattern 类型
- ✓ 不矛盾：说 CPU IMA prefetcher "在 CPU 上取得了显著加速"（维度：CPU 性能）→ 再说它"设计假设与 GPU 冲突"（维度：GPU 适用性）
- ⚠️ 注意：前面说"Spare Register 取得了 10% 加速"，后面不能说它"无效"。应该说它"受限于 Fermi 架构和单层 load-pair"（限制条件维度）

## §4 文献点评

> 这部分承担的任务：展示已有研究的脉络，指出剩余 gap，为本文工作创造逻辑必然性。

### How / Why / So What 框架

**是什么**：一条高质量的文献点评，至少要回答三个问题：**怎么做的（How）**、**为什么有效（Why）**、**结果是什么（So What）**。只说 So What 的点评是"综而不述"。

**怎么做**：

- **How** = 方法/路径："IMP uses address differentials to infer the shift between index and data arrays"
- **Why** = 机制/原因："because indirect accesses A[B[i]] produce address patterns where consecutive data addresses differ by a fixed shift"
- **So What** = 结果/效果："achieving 56% average speedup across graph workloads"
- 三者不需要每次都完整出现，但 **How 不能缺**——否则读者看完只记得一个泛泛结论
- 原始例子（第 5 讲）：只写"某方法取得了 X% 加速"是不完整的——"读者看完只记得一个泛泛的结论"。好的写法是先提炼多篇文献的共性做法/共性发现/共性局限，再在必要时补一个代表性案例

**为什么**：文献点评不是点名册。完整的 How/Why/So What 让读者抓住研究思路、机理依据和效果输出的完整逻辑。否则读者会追问"怎么做到的？""为什么？"

**GRASP 映射**：

- ✓ 完整点评："IMP detects indirect patterns by computing address differentials and matching them against candidate shifts (How), exploiting the structural relationship between index and data arrays (Why), achieving 56% average speedup (So What) [Yu, MICRO'15]."
- ✗ 不完整（仅 So What）："IMP achieves 56% speedup [Yu, MICRO'15]." — 读者不知道怎么做到的
- ✗ 不完整（仅 How）："IMP uses address differentials to detect patterns [Yu, MICRO'15]." — 读者不知道效果如何
- 实际操作建议：Introduction 中每篇关键文献至少给出 How + So What，Why 在空间紧张时可以省略

---

### 原则十二：在必要处引入画面感

**是什么**：在最容易抽象、最容易让读者一眼滑过去的地方，补一个**具体、可感的细节**。不是每句话都需要画面化。

**怎么做**：

- 找到高抽象度的句子（通常是连续的术语堆叠）
- 补入一个具体名词、数字、对象或示意细节
- 原始例子（第 5 讲）：不只说"离子可逆插入/脱出"，而是给出具体离子名（Li⁺、K⁺），"读者一下就更容易形成脑内图像"。这类处理能明显降低阅读障碍

**为什么**：纯抽象的文字让读者大脑"滑过去"而不留下印象。一个具体细节可以让整句话"立"起来。

**GRASP 映射**：

- 抽象版："IMA patterns cause poor cache performance" — 太泛，读者滑过去
- ✓ 画面感版："A single BFS iteration accesses neighbor lists scattered across a 2 GB adjacency array — addresses that cannot be known until the index load returns from L2" — 读者立刻有了 scatter 访问的画面
- ✓ 另一个例子：直接给出 SASS 指令 `IMAD.WIDE Rd, Rindex, Rscale, c[0x0][0x1XX]` — 让读者看到 ISA 暴露的结构，比说"GPU ISA provides structural information"有力得多

---

### 原则十三：后句必须咬住前句

**是什么**：每句话都要建立在前一句的基础上**延续、扩展或转折**。不能突然跳到一个新话题。用 However / Moreover / Therefore 等信号词表明句间关系。

**怎么做**：

- 写完一句话后，检查下一句是否从前句自然延伸
- 用信号词明确逻辑关系：Moreover（延续）、However（转折）、Therefore（结论）
- 文献点评里指出的局限，**最后都必须能被本文方案接住**——否则你指出的问题越多，只会越显得自己的工作不解决关键矛盾
- 原始例子（第 5 讲）："后一两句必须紧贴前一句或前两句，本质是保证文段内部的力线不断掉"。前文说酸性环境利于 MnO₂、碱性环境利于 Zn，看似互相冲突，后文用"解耦"把这对矛盾变成本文工作的入口

**为什么**：句间逻辑断裂是阅读体验的头号杀手。一旦读者感到"怎么突然跳到这了"，信任度直线下降。

**GRASP 映射**：

- 钳形叙事的咬合链示例：
  1. "CPU 社区在 IMA 上积累了 10 年经验..."（立论）
  2. **"However,** these approaches assume..."（转折：迁移障碍）
  3. **"Meanwhile,** GPU prefetching has evolved..."（并列：另一路线）
  4. **"Yet** none of these targets data-dependent accesses..."（转折：盲区）
  5. **"Therefore,** GPU IMA prefetching remains an open problem..."（结论：钳形闭合）
- ⚠️ 检查：introduction.md 中的过渡句必须形成完整的逻辑咬合，不能有断裂

---

### 总分嵌套结构

**是什么**：文献点评不是一篇篇列下去，而是**先总括核心问题（总）→ 分别展开每个问题（分）→ 分中再套总分**。嵌套结构给读者提供骨架感。

**怎么做**：

- 先写一句总括（本段讨论哪几个核心问题）
- 再分别展开每个问题：先概括该方向做到了什么，再给代表性案例，再指出剩余 gap
- 原始例子（第 8 讲）：第二段先总括两个核心问题（工作寿命受限、能量效率低），再分别展开。"这个'总'非常关键，因为它决定后面所有文献材料该往哪里放，也决定读者要用什么框架理解后续细节"

**为什么**：没有总分结构的文献点评会变成"材料堆积"，读者只能自己猜作者想表达什么。有了骨架，读者在任何一句话处都知道"这句在论证哪个问题"。

**GRASP 映射**：

```
总: GPU IMA prefetching 的空白来自两个方向的各自局限

  分1（CPU 路线）:
    总: 10 年积累，两条路线（硬件 / 软件）
    分: IMP → DMP → Tyche（硬件）; Prodigy → Magellan（软件）
    总: 但四大迁移障碍（warp 交织 / 小 L1 / PC 膨胀 / 存储预算）

  分2（GPU 路线）:
    总: 15 年进化，四代 prefetcher
    分: Many-Thread → Orchestrated → CAPS → Snake
    总: 但全部假设 stride pattern，从未触及 IMA

再总: 钳形闭合 → GPU IMA prefetching 是交叉空白
```

### 原则十四：水泥与砖块比例

**是什么**：

- **砖块** = 基于文献事实、数据、结论的直接转述。判断标准**不是有没有提人名**，而是内容是否在转述文献已有结果
- **水泥** = 作者的概括（跨多篇文献的共性提炼）、第一性原理解释、逻辑连接词（However / Moreover / Therefore）、研究方向判断
- 砖块过多 → "综而不述"的流水账，读者只能自己猜脉络
- 水泥过多 → "观点多证据少"，读者怀疑你是否了解领域

**怎么做**：

- **砖块定向选取**：优先选能直接支撑标题核心贡献的文献结果。同样研究同一对象，如果你要解决的是不同痛点，就该选不同的砖块
- **水泥包裹砖块**：先用水泥概括方向 → 再用砖块（代表性案例 + 数据）支撑 → 再用水泥做小结和过渡
- **引用位置暴露身份**：如果一句话前半是文献数据（砖块）+ 后半是作者推论（水泥），引用**只该跟在前半后面**，不要把后半也伪装成文献原话
- 原始例子（第 8 讲）：选砖块要问"为什么选这些文献结果，而不选别的？"答案应该是"因为它们正好对应标题中的核心贡献关键词"。范文选的两类砖块正好对应标题中的 High Energy Efficiency 和 Long Life

**为什么**：砖块提供可信事实，水泥提供结构和方向。两者合起来，才能让读者相信：这个领域确实到了这个阶段，确实还剩这些问题，本文确实应该做这件事。

**GRASP 映射**：

- 砖块示例："IMP achieves 56% average speedup using address differential matching [Yu, MICRO'15]" — 纯文献转述
- 水泥示例："Each generation addresses a new dimension — from single-level to multi-level to non-linear patterns — yet all remain CPU-centric." — 作者跨多篇文献的概括
- 混合句示例："CAPS detects stride patterns with 97% accuracy [Koo, IPDPS'18]**（砖块）**, but explicitly excludes data-dependent accesses — the very pattern that IMA embodies**（水泥）**."
  - 引用只跟在前半（CAPS 的数据）后面，后半是作者的推论
- 选砖标准：标题强调 ISA-Exposed 和 Register-Chain → 选能突出"已有方案依赖黑盒推断"的砖块（IMP 的 shift 试探、DMP 的差分匹配、Spare Register 的 tag 传播 → 都是黑盒）→ 对比凸显 GRASP 的 ISA 白盒优势

## §5 引出本文工作与收口

> 这一段的任务：从前文 gap 自然引出 GRASP，用标题关键词和选取的结果完成逻辑闭环。

### 标题关键词集中亮相

**是什么**：标题中真正代表作者独有贡献的词，在背景铺垫阶段不会频繁出现。它们在前言最后段（引出本文工作时）**集中亮相**——这是逻辑上"正式讲我做了什么"的信号。

**怎么做**：

- 识别标题中的贡献性关键词
- 检查它们是否在背景段被过早/过频使用
- 确认它们在最后段高密度出现
- 原始例子（第 6 讲）：`Decoupling` 在背景段不出现，在最后段高密度出现。"这类词往往不会在背景铺垫阶段频繁出现，因为那时前言的任务是立住研究对象、问题和需求，而不是过早把创新硬塞出来"

**为什么**：过早暴露创新词会分散注意力，也可能在读者还没理解 gap 的时候就开始"推销"。让创新词在最后段集中出现，产生的冲击力更大。

**GRASP 映射**：

- 贡献性关键词：**ISA-Exposed / Register-Chain / IMAD.WIDE / GRASP**
- 这些词在 §1.1-§1.3（背景段）应该极少出现或不出现
- 在 §1.4（引出本文工作）高密度出现：
  - "We observe that GPU's **IMAD.WIDE** instruction structurally exposes..."
  - "...**register-chain** detection requires only a single instruction observation..."
  - "...we propose **GRASP** (GPU **Register-chain** Aware Sector Prefetcher)..."

### 结果选取标准

**是什么**：前言最后一段**不该把所有结果都倒出来**。只选最能呼应标题、最能填前文 gap 的结果。

**怎么做**：

- 选取标准不是"我最喜欢哪条数据"，而是"哪条结果最直接回应标题和前文提出的问题"
- 原始例子（第 6 讲）：标题说 "High-Energy Stable Battery" → 选电压数据（回应 high-energy）+ 循环稳定数据（回应 stable）。不把所有性能指标都塞进去。"前言最后一段不是结果堆砌，而是只挑最亮眼、最能呼应标题的几条结果"

**为什么**：前言是引导读者进入论文的通道，不是 abstract 的翻版。选择性地展示结果，反而能引导读者带着期待去读 evaluation。

**GRASP 映射**：

| 标题关键词 | 应选取的结果 |
|-----------|-------------|
| GPU Indirect Memory Patterns | IMA coverage/accuracy 数据（证明确实在 "grasping" patterns） |
| ISA-Exposed | 检测延迟对比（1 次指令观测 vs IMP 地址序列 vs Spare Register 3 次迭代） |
| Prefetching | Speedup 数据（最终性能提升） |

不应在前言列出的结果：MSHR 拥塞细节、throttle 参数、具体 SM 数量配置等

### 逻辑闭环：前文挖的坑，后面都要填

**是什么**：好前言的闭环感来自"前面挖的每个坑，最后段都有对应结果填上"。如果前面列了问题 A，后面的方案没有回应 A，逻辑就塌了。

**怎么做**：

- 列出前文所有 gap / 问题陈述
- 对每个 gap 检查：最后段是否有对应的回应（方案描述或结果数据）
- 原始例子（第 6 讲）：前文说"锌空气电池低工作电压" → 最后段给出"2.5V+（vs baseline 1.5V）"，精确填坑。"逐项回看前文提出的痛点，看最后一段是否真的把它们一一填平"

**为什么**：逻辑闭环是审稿人评价 Introduction 质量的**最核心标准**。前面的问题就是对读者的承诺，不兑现等于失信。

**GRASP 映射**：

| 前文 Gap | 最后段应回应 |
|---------|------------|
| IMA 占 L1 miss 51-84%，导致巨大性能损失 | GRASP 的 IMA data coverage 和 speedup 数据 |
| CPU IMA 方案无法迁移（黑盒推断、per-core 状态） | GRASP 用 ISA 白盒提取，per-SM 共享表 |
| GPU stride prefetcher 排除/无法处理 IMA | GRASP 专门针对 IMA 的 index-data pipeline |
| Spare Register 仅 Fermi + 单层 + tag-based | GRASP 在 SM80/A100 + one-to-many + 1 次观测 |
| Ideal L1D 天花板 1.75×-3.04× | GRASP 达到天花板的 Y%（待实验数据填入） |

### 第一段（问题定义）

- [ ] 首句的概念层级与标题最高层概念距离 ≤ 2 层（原则四）
- [ ] 概念层级单向下降，没有回跳（原则二）
- [ ] 2-3 层内进入研究对象（原则三）
- [ ] 每句话能追溯到标题中的某个关键词（原则一）

### 过渡段（铺垫 + 文献回顾）

- [ ] 所有非标题直接相关的句子都通过了"值回票价"检验（原则六）
- [ ] 用了读者熟悉的对象做认知桥梁（原则七）
- [ ] 批评他人工作时措辞克制 + 紧跟证据（原则八）
- [ ] 所有量化暗示词（"很多 / 主流 / 关键"）通过了半定量审查（原则九）
- [ ] 技术判断有真实世界 / 规格书验证（原则十）
- [ ] 同一对象的优缺点落在不同维度（原则十一）

### 文献点评段

- [ ] 每条关键文献至少有 How + So What（How/Why/So What 框架）
- [ ] 高抽象处有具体细节提供画面感（原则十二）
- [ ] 每句话建立在前句基础上，信号词明确（原则十三）
- [ ] 有总分嵌套结构：先总括问题 → 分别展开 → 指出 gap
- [ ] 砖块（文献事实）定向服务标题核心贡献（原则十四）
- [ ] 水泥（作者概括）和砖块比例适当，没有流水账也没有空口白话（原则十四）

### 本文工作段

- [ ] 标题贡献性关键词在此段集中出现，背景段极少出现
- [ ] 只选了最能呼应标题 + 最能填 gap 的结果
- [ ] 前文挖的每个坑，都有对应回应（逻辑闭环表）
- [ ] 第零上位已在前文被明确引出

### 全文通检

- [ ] 每个性能词 / 优势词 / 场景词，后文都有对应结果支撑（原则五）
- [ ] 对标题中后文会重点展开的关键词做了删除测试
- [ ] 参考范文时，背景句和自己的研究场景 / 应用方向严格匹配（原则五延伸）
- [ ] 前言中提到的所有问题，后文方案都能接住（原则十三延伸）
